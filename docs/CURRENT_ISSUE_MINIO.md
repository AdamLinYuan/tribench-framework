# Current Issue: MinIO Cluster Initialization Failure

**Date:** 23 November 2025

## Problem Description
We are attempting to create the `iceberg.tpch` schema in Trino to proceed with the `tpch-iceberg-tiny` experiment. The operation fails with `TrinoUserError: Invalid location URI: s3://warehouse/tpch`.

Upon investigation, the root cause appears to be that the MinIO storage backend is not correctly initialized, preventing Hive Metastore and Trino from interacting with it.

## Symptoms
1. **Trino Error**: `CREATE SCHEMA` fails when specifying the `s3://` location.
2. **MinIO Client Failure**: Running `mc ls local/warehouse` inside the `tribench-minio-0` pod fails with `Server not initialized yet`.
3. **Missing Credentials**: `mc alias list` inside the pod shows empty AccessKey and SecretKey for the `local` alias.
4. **Log Errors**: The MinIO logs (`kubectl logs -n tribench tribench-minio-0`) show that the node is unable to connect to other nodes in the cluster. It is waiting for a minimum of 8 drives (nodes) to come online but cannot find them.

## Log Snippet
```
INFO: Unable to use the drive http://tribench-minio-0.tribench-minio-svc.tribench.svc:9000/export: drive not found, will be retried
INFO: Unable to use the drive http://tribench-minio-1.tribench-minio-svc.tribench.svc:9000/export: drive not found, will be retried
...
INFO: Unable to use the drive http://tribench-minio-15.tribench-minio-svc.tribench.svc:9000/export: drive not found, will be retried
INFO: Waiting for a minimum of 8 drives to come online (elapsed 17m19s)
```

## Hypothesis
The MinIO cluster is configured to run in distributed mode (likely expecting 16 drives/nodes based on the logs), but the nodes cannot communicate with each other or the volume mounts are incorrect.

Possible causes:
1. **DNS/Service Issue**: The headless service `tribench-minio-svc` might not be correctly resolving the pod hostnames.
2. **Misconfiguration**: The startup command for MinIO might be listing endpoints that don't match the actual Kubernetes StatefulSet replicas.
3. **Volume Issues**: The `/export` path might not be mounted correctly.

## Next Steps
1. **Inspect Manifests**: Check the generated MinIO Kubernetes manifests (likely in `systems/kubernetes/` or generated by `lib/tribench/systems/minio.py`) to verify the startup command and replica count.
2. **Verify Pod Status**: Ensure all 16 pods (if that's the intended count) are running.
3. **Check DNS**: Exec into a pod and try to `nslookup` the peer hostnames.
4. **Reset/Scale Down**: If a 16-node cluster is unnecessary for this test, reconfigure MinIO to run as a single replica or a smaller cluster (e.g., 4 nodes) to simplify the topology.

## Additional Findings
- **Deployment Mismatch**: The `lib/tribench/systems/minio.py` file contains logic to deploy MinIO via Docker Compose as a single standalone instance. However, the current environment is running on Kubernetes with a StatefulSet of 16 replicas.
- **Configuration Source**: The Kubernetes deployment is likely managed by a Helm chart using `systems/kubernetes/minio-values.yaml`. The values file does not explicitly set the replica count, implying it defaults to the chart's default or is overridden elsewhere.
- **Root Cause Probability**: The distributed mode (16 nodes) requires strict DNS and connectivity between pods. The logs indicate this peer discovery is failing. A single-node deployment (standalone) would likely be sufficient for this benchmark and much more stable.

## Recommendation
Modify the Kubernetes deployment to run MinIO in standalone mode (1 replica) to bypass the distributed clustering issues. This involves:
1. Scaling down the StatefulSet to 1.
2. Updating the startup command to run in standalone mode (e.g., `minio server /data`) instead of distributed mode (which usually looks like `minio server http://...`).
