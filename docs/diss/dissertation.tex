\begin{abstract}
    Over the past decade, large-scale analytical systems have undergone a structural transformation. The data lakehouse architecture, which combines the low-cost object storage of a data lake with the ACID transactional guarantees of a data warehouse, has emerged as a dominant pattern for enterprise analytics. Apache Iceberg, an open table format that provides snapshot isolation, time-travel queries, and schema evolution on top of columnar Parquet files, has become a cornerstone of this architecture. Apache Trino, a distributed SQL query engine capable of federating queries across heterogeneous data sources, is increasingly deployed as the interactive query layer over Iceberg-based lakehouses in production environments.

    Despite the maturity of this stack, the ecosystem currently lacks a reproducible, systematic benchmarking framework for Trino comparable to what PEEL provides for Apache Spark. Existing tools either require significant manual configuration per run, lack integrated hardware monitoring, or cannot port across deployment environments without modification. This creates a reproducibility problem: performance results reported in one environment cannot reliably be reproduced in another, and the effort required to re-run experiments from scratch discourages rigorous empirical evaluation.
    
    We propose TriBench, a cross-platform framework that addresses this gap by providing structured batch workload execution, concurrent hardware resource monitoring, and persistent result storage in a configuration-driven, portable bundle. TriBench supports both Docker-based local deployments and Kubernetes-based distributed cluster deployments, allowing the same experiment specification to execute on a developer laptop or a multi-node school cluster without modification.The framework is evaluated using the TPC-H benchmark suite at multiple scale factors across three distinct environments: a local Docker deployment, an institutional Kubernetes cluster at the School of Computing Science, and a managed cloud deployment using Google Kubernetes Engine (GKE) demonstrating repeatable query execution with full hardware telemetry across all environments.
    
    The results show that TriBench successfully orchestrates reproducible experiments, captures CPU, memory, disk I/O, network I/O, and per-pod Kubernetes metrics concurrently with query execution, and persists results in a structured store that supports downstream analysis and cross-run comparison. The framework fulfils the identified need for a PEEL-equivalent systematic benchmarking tool in the Apache Trino ecosystem.

    
\end{abstract}

\section{Motivation}
\label{sec:motivation}

The data lakehouse has become a common architectural pattern for modern analytics
pipelines \citep{armbrust2021lakehouse}, combining low-cost object storage with
warehouse-style reliability and performance through an open table-format layer.
Apache Iceberg \citep{apache_iceberg} is widely used to provide this table abstraction,
while Apache Trino \citep{sethi2019presto} provides the distributed SQL execution layer
that queries Iceberg tables at interactive speeds.

Evaluating the performance of such a stack is non-trivial. An engineer wishing to compare
the effect of different worker counts, Iceberg partitioning strategies, or JVM heap
settings must: provision the full storage and metadata service stack, generate or load a
dataset at a controlled scale factor, execute a standardised query suite, and capture
hardware metrics throughout---all in a manner reproducible enough for the results to be
scientifically comparable. For the Apache Spark ecosystem, the PEEL framework
\citep{peel_github} provides exactly this scaffolding. For Apache Trino, no equivalent
open tool exists. Engineers either write ad-hoc scripts that are not reusable across
machines, or assemble workflows in general-purpose orchestration tools such as Apache
Airflow that lack native benchmarking abstractions.

TriBench is designed to close this gap. It takes inspiration from PEEL's bundle-based
approach---where a single configuration-controlled directory encodes environment, workload,
and result specifications---and extends it with a first-class bundle system for Trino
deployments. A TriBench bundle is a self-contained directory identified by a
\texttt{bundle.yaml} manifest, with dedicated sub-directories for configuration profiles,
experiment definitions, datasets, query files, logs, and a per-bundle results database.
Bundles can be created with via Tribench CLI commands, archived as \texttt{.tar.gz} snapshots, and shared across
machines---providing the same environment isolation properties that make PEEL bundles
reproducible, while adding integrated real-time hardware monitoring and transparent support
for both single-node Docker and distributed Kubernetes backends.

\section{Goals}

The goals of this project are stated below. These identifiers are used consistently through the dissertation and are mapped to evaluation evidence in the Evaluation Chapter.

\textbf{(1) Execute benchmark workloads.}
The first goal of TriBench is to provide a means of executing SQL benchmark workloads
against a running Trino cluster.
\begin{itemize}
    \item The framework should support industry-standard analytical benchmark suites as well as user-defined SQL workloads.
    \item Users should be able to supply their own datasets alongside the built-in benchmark data.
    \item Each experiment should be described in a declarative configuration file, without requiring changes to the framework itself.
    \item Execution behaviour---such as warmup strategy, number of repetitions, and query concurrency---should be configurable per experiment.
    \item Related experiments should be groupable into suites that execute end-to-end as a single operation, with the framework handling environment start-up and teardown automatically.
\end{itemize}

\textbf{(2) Monitor hardware resource usage.}
The second goal is to capture hardware telemetry concurrently with query execution.
\begin{itemize}
    \item The framework should record host-level resource utilisation, including CPU, memory,disk, and network activity, throughout each experiment.
    \item In distributed deployments, per-node metrics should additionally be collected for each component of the Trino cluster.
    \item The framework should also record query-level performance statistics reported by the query engine, such as execution time and data volume processed.
\end{itemize}

\textbf{(3) Persist and export benchmark results.}
The third goal is to store results in a structured form that supports post-hoc analysis and cross-run comparison.
\begin{itemize}
    \item Results should be held in a queryable structure that separates run metadata, per-query outcomes, and time-series hardware metrics.
    \item Stored results should be exportable into common formats for use in external analysis tools.
    \item Each run should receive a unique identifier so that repeated executions accumulate rather than overwrite historical results.
\end{itemize}

\textbf{(4) Scale across deployment environments.}
The fourth goal is for the same experiment specification to run without modification on
both a local single-node deployment and a distributed cluster.
\begin{itemize}
    \item For local development, the framework should automatically manage the full data lakehouse stack through a command-line interface.
    \item For distributed experiments, the same stack should be deployable on a container-orchestrated cluster with transparent connectivity for the benchmarking client.
    \item Named configuration profiles should allow an engineer to switch the entire deployment context---cluster size, resource allocation, backend type---with a single command and without modifying any experiment file.
\end{itemize}

\textbf{(5) Provide portable, self-contained experiment bundles.}
The final goal is to organise all experiment artefacts into a self-contained bundle that
isolates one study's configuration, datasets, and results from others.
\begin{itemize}
    \item A bundle should be creatable with a single command, producing a standard directory layout with annotated template files as starting points.
    \item Activating a bundle should cause all framework operations to resolve automatically within that bundle's directory.
    \item A completed bundle should be archivable as a single portable file to enable long-term storage and reproduction on a different machine.
\end{itemize}

\section{Data Lakehouse Architecture}

The evolution of modern analytics platforms can be understood as a progression from data warehouses to data lakes, and finally to the data lakehouse pattern \citep{armbrust2021lakehouse}. Early data warehouses centralised curated data for decision support and business intelligence. They typically used a schema-on-write approach: data was transformed on ingest into a fixed model designed for predictable analytical queries. This provided strong governance and excellent performance, but often at the cost of tight coupling between storage and compute, expensive scaling as data volumes grew, and limited support for semi-structured or unstructured data.

Data lakes emerged to address these constraints by separating storage from compute. Raw data could be stored cheaply in generic file systems or object stores, commonly using open columnar formats such as Apache Parquet \citep{vohra2016apache}. This schema-on-read model improved agility and reduced cost, but it introduced new problems: without a transactional coordination layer and consistent metadata, concurrent writers can leave a dataset in an inconsistent state, and query engines may be forced into large scans because they lack reliable file- and partition-level statistics.

The \emph{data lakehouse} approach aims to combine the openness and cost profile of data lakes with the management properties of warehouses. It does so by introducing an open table format layer that maintains transaction state and query-relevant metadata alongside the data files. Apache Iceberg \citep{apache_iceberg} is a prominent implementation. An Iceberg table is defined by a metadata tree: a \emph{metadata file} points to the current \emph{snapshot}, which references a \emph{manifest list} of \emph{manifest files} describing the underlying Parquet objects, including column statistics. This metadata enables optimisations such as partition pruning and predicate pushdown, substantially reducing the amount of data that must be read for many analytical queries.

To make these tables discoverable via SQL, Iceberg deployments use a catalogue service that maps logical table names to metadata locations. In TriBench's stack, the Hive Metastore Service (HMS) fulfils this role, persisting catalogue state in a relational backend. Apache Trino \citep{sethi2019presto}---the distributed SQL engine that forms the compute layer of the stack---consults the catalogue during query planning to resolve the current metadata pointer for each referenced table. Trino operates under a coordinator--worker model: a coordinator node parses and plans queries, then distributes execution as parallel tasks across worker nodes that read Parquet data directly from object storage. This architecture allows the same experiment to scale from a single-node Docker deployment to a multi-node Kubernetes cluster by adjusting the worker replica count, without any change to the query workload or experiment specification.

\section{Benchmarking for Distributed SQL Systems}

Benchmarking is the practice of evaluating a system's performance using a controlled workload. According to \citet{gray1993benchmark}, a useful benchmark must possess four properties: relevance, portability, scalability, and simplicity. The Transaction Processing Performance Council (TPC) provides the industry-standard suites that satisfy these criteria for analytical SQL workloads; the specific benchmarks used in this work are described in Section~\ref{sec:tpc}.

Benchmarking distributed SQL engines introduces significant complexity beyond single-node systems. Because queries execute as parallel jobs across multiple machines, end-to-end latency reflects not just computational work but also scheduling overhead, network exchanges, and remote storage throughput. This makes reproducibility---discussed in Section~\ref{sec:reproducibility}---a central concern: without tight control over environment, data layout, and execution parameters, results from one run cannot be meaningfully compared with another.

\section{TPC Benchmark Standards}
\label{sec:tpc}

Founded in 1988, the Transaction Processing Performance Council (TPC) is a non-profit organisation dedicated to developing and maintaining data-centric benchmark standards and disseminating objective, verifiable performance data to industry \citep{tpch2023}. TPC benchmarks are divided into \emph{Enterprise} benchmarks---technology-agnostic, specification-based standards where vendors choose their own implementation---and \emph{Express} benchmarks, which are kit-based with shorter development cycles.

TPC-H \citep{tpch2023} is a decision-support benchmark that models a supply-chain scenario with 22 business-oriented ad-hoc queries. The dataset and queries are designed for broad industry relevance, exercising decision-support systems that examine large volumes of data and execute queries with a high degree of complexity. Scale is controlled by a \emph{scale factor} (SF): SF1 generates approximately \SI{1}{GB} of raw data across eight related tables. The primary performance metric is the TPC-H Composite Query-per-Hour Performance Metric (QphH@Size), which captures both single-stream query latency and multi-user query throughput. TPC-H is the primary built-in benchmark suite shipped with TriBench: all 22 queries are included in the repository under \texttt{apps/tpch/queries/}, pre-adapted to Trino-compatible SQL and parameterised by Iceberg catalogue and schema name so they can be used out of the box against a loaded dataset.

TPC-DS \citep{tpcds2021} extends the decision-support model to a complex retail scenario with 99 queries testing advanced SQL features such as window functions, complex joins, and nested subqueries. It models query response time in single-user mode, query throughput in multi-user mode, and data-maintenance performance. TPC-DS is the second built-in benchmark suite: its query files are similarly bundled in the repository under \texttt{apps/tpcds/queries/}, and TriBench's dataset registry and query-loader are structured to load and execute them against an Iceberg schema in exactly the same way as TPC-H, without any framework modification.

\section{Reproducibility in Systems Research}
\label{sec:reproducibility}

Reproducibility is a foundational property of scientific experimentation, defined by \citet{jain1991art} as the ability for an independent experimenter to obtain consistent results under identical conditions. In systems research, meeting this definition in practice requires capturing not just the software configuration but also the hardware environment, dataset state, and execution parameters---all of which interact in a distributed SQL system.

The distributed systems research community has long recognised this challenge. A typical performance study requires coordinating multiple interdependent services---storage, catalogue, and compute engine---each with its own configuration. Without a systematic means of recording and replaying these configurations, reported results are difficult to verify and cannot be reproduced on a different machine. \citet{peel_github} articulated this directly: practitioners are typically forced to choose between manually steering experiment lifecycles---an error-prone and non-reproducible process---or writing ad-hoc scripts that embed environment-specific assumptions. Both approaches produce artefacts that cannot be shared or re-run without significant manual effort.

Achieving reproducibility in distributed SQL benchmarking requires strict control over four dimensions that directly motivate the design of TriBench:
\begin{enumerate}
\item \textbf{Environment Specification:} Precise control over cluster configuration, including worker counts, CPU and memory limits, and JVM heap settings.
\item \textbf{Data Consistency:} Loading the dataset at an identical scale factor with the same physical layout and Iceberg partitioning strategy across runs.
\item \textbf{Execution Control:} Standardising the warmup policy, query execution order, and concurrency model so that variance between runs reflects only system behaviour.
\item \textbf{Measurement Capture:} Recording both query-level statistics (wall-clock time, CPU time, bytes scanned) and concurrent system-level telemetry (CPU utilisation, memory pressure). Capturing both is essential, as resource saturation often manifests in hardware metrics before it is visible in query latency.
\end{enumerate}

The TriBench design maps each of these dimensions to a specific mechanism, as described in Chapter~\ref{chap:design}: named profiles control environment specification, the dataset registry enforces data consistency, experiment YAML files standardise execution, and the concurrent monitoring subsystem handles measurement capture.

\section{Benchmarking Frameworks for Distributed Systems}
\label{sec:benchmarking_frameworks}

\subsection{PEEL}

TriBench builds on PEEL \citep{peel_github}, a framework developed at TU Berlin for reproducible experiments on distributed data processing systems (Apache Spark, Flink, Hadoop). Evaluating modern distributed systems differs from benchmarking traditional RDBMSs: realistic experiments coordinate multiple interdependent services---distributed file system, processing engine, monitoring tool---each with hardware-dependent configuration. Manual administration across parameter sweeps is tedious and error-prone, producing artefacts that cannot be shared or reproduced on different hardware.

PEEL introduces the experiment \emph{bundle} as its central abstraction: a self-contained, portable directory packaging workload applications, configuration files, data generators, datasets, system binaries, and result logs. Experiments are defined as Spring Dependency Injection beans in Scala, specifying workload command, run count, input datasets, expected outputs, and dependent \emph{System} beans with \emph{lifespan} (\texttt{Provided}, \texttt{Suite}, \texttt{Experiment}, \texttt{Run}). PEEL starts and stops these systems automatically. Hardware telemetry collection uses a \texttt{dstat} system bean dependency, triggering dstat on all nodes before execution.

Environment configuration uses a layered HOCON hierarchy: framework defaults (\texttt{reference.peel.conf}) overridden by bundle-level files (\texttt{config/}), then host-specific files (\texttt{config/hosts/\$HOSTNAME/}), then experiment bean config. This allows bundles to run on different hardware without modifying experiments---TriBench adopted this design for its four-level HOCON hierarchy.

After suite completion, PEEL invokes an ETL pipeline parsing raw log files, transforming heterogeneous output into a unified relational schema, and loading results into a database (H2 or MonetDB). Experimenters query historical runs in SQL and connect to reporting tools (JasperReports, Tableau).

PEEL established the bundle paradigm and layered HOCON model TriBench inherits, but two gaps limit applicability to modern lakehouse stacks. First, system bindings target Hadoop-era engines on bare-metal or YARN; no support for container-orchestrated Kubernetes deployments or Trino--Iceberg--MinIO composition. Second, telemetry collection is post-hoc: dstat output is gathered from log files after runs. TriBench captures concurrent hardware metrics in real time via background threads and queries Trino's REST API for per-query CPU time and bytes scanned during execution. TriBench modernises PEEL's foundations---portable bundles, layered configuration, database-backed storage---for distributed SQL lakehouses.

\subsection{LST-Bench}

LST-Bench \citep{2024lstbench} evaluates Log-Structured Tables (Delta Lake, Apache Iceberg, Apache Hudi) on cloud object storage. Developed by Microsoft Research, it extends TPC-DS with composable workload patterns addressing LST-specific characteristics: longevity (performance degradation under frequent updates), resilience (compaction and maintenance impact), read/write concurrency (concurrent query and update sessions), and time travel (historical table queries). It quantifies degradation rate as delta files accumulate and automates telemetry from compute engines and cloud storage APIs to measure latency, throughput, storage efficiency, and compute utilization. LST-Bench compares table format performance, assuming engine and storage infrastructure are already provisioned. It does not manage deployment lifecycle of Trino, Hive Metastore, or object storage, nor provide bundle-based isolation or declarative profiles. TriBench is complementary: it provides the reproducible deployment harness and configuration management for executing LST-Bench workloads across environments.

\subsection{DiPerf}

DiPerF \citep{diperf} automates performance measurement of Grid computing networked services (GridFTP, GRAM, WS-MDS from Globus Toolkit). DiPerF coordinates distributed client machines concurrently accessing a target service, collects per-client response time and throughput, performs clock reconciliation across geographically dispersed nodes, and aggregates results into service-level statistics (fairness, saturation point). Its architecture cleanly separates concerns---controller distributes client code to testers, testers time requests, offline analyser summarises performance samples---influencing TriBench's orchestration/monitoring/storage layer separation. However, DiPerF assumes the target service is deployed and running; it provides no provisioning or teardown mechanism. TriBench addresses this gap: it manages the full lakehouse service lifecycle (Trino, Hive Metastore, MinIO, PostgreSQL), captures per-query SQL statistics from Trino's REST endpoint alongside concurrent hardware telemetry, and uses bundle abstraction and HOCON hierarchy to guarantee reproducibility across deployments. DiPerF measures service response to distributed load; TriBench measures lakehouse end-to-end performance under controlled analytical workload.

\section{Alternative Approaches to Performance Evaluation}

Without dedicated benchmarking frameworks, practitioners evaluating distributed SQL engines resort to ad-hoc scripting, general-purpose workflow orchestration, cloud-managed services, or manual processes. Each presents fundamental limitations motivating TriBench's design.

\subsection{Ad-hoc Scripting}

Engineers write shell scripts or Python notebooks to start services, execute queries, and collect timing measurements. While flexible, these scripts embed environment-specific assumptions (hard-coded connection parameters, absolute paths, cluster sizes) preventing unmodified execution on different machines. Scripts typically capture only query latency, ignoring concurrent hardware telemetry, and store results as flat files or unstructured logs rather than queryable schemas supporting historical comparison. Scripts are rarely version-controlled alongside dependent data and configuration, making reproduction after cluster upgrades or configuration drift nearly impossible.

\subsection{Workflow Orchestration Tools}

General-purpose workflow orchestration tools (Apache Airflow, Dagster, Prefect) are sometimes repurposed for benchmarking. These systems excel at scheduling recurring tasks and managing production pipeline dependencies, but lack native abstractions for benchmark-specific concerns. Airflow Directed Acyclic Graphs (DAGs) invoke SQL and collect execution times, but provide no built-in support for warmup runs, parameterised query templates, or automatic hardware monitoring. Critically, Airflow orchestrates operational workflows---triggering incremental ETL jobs---not controlled scientific experiments requiring environment teardown between runs to eliminate cache effects. Adapting Airflow for reproducible benchmarking requires substantial custom code to manage system lifecycle, capture telemetry, and isolate experiment state, effectively reimplementing a dedicated framework.

\subsection{Cloud-Managed Analytics Services}

Cloud-managed analytics services (Google BigQuery, Amazon Redshift, Azure Synapse) offer built-in query performance dashboards and cost attribution, eliminating manual telemetry collection in production workloads. However, these tools measure performance within a single vendor's managed stack and do not support cross-environment comparisons---critical for evaluating open-source engines like Trino deployable to Docker, Kubernetes, or bare metal. Managed services abstract underlying infrastructure configuration, preventing study of worker count, JVM heap size, or storage backend effects on query latency. TriBench provides full deployment stack control while automating telemetry capture.

\subsection{Manual Processes}

Manual processes remain common in academic research and vendor whitepapers: engineers provision clusters through cloud consoles, manually upload datasets, run queries from SQL clients, and record execution times in spreadsheets. This suits one-off exploratory studies but fails when experiments require repetition across parameter sweeps or sharing with collaborators. Lack of automation introduces human error (forgetting cache clears, misrecording timestamps, losing configuration details). Absence of version-controlled experiment definitions makes verifying reproduction attempts with identical settings impossible. TriBench eliminates these failure modes by encoding all configuration as declarative YAML and HOCON files executing deterministically.

\section{Lakehouse Technologies and Container Orchestration}

TriBench benchmarks the Trino--Iceberg lakehouse stack across Docker and Kubernetes deployments. This section surveys the core technologies under test and the container orchestration platform enabling reproducible distributed deployments.

\subsection{Apache Iceberg}

Apache Iceberg is an open table format that manages how data files are organised, versioned, and exposed as a single queryable table \citep{apache_iceberg}. Each table maintains a metadata layer recording the schema, partitions, and per-file statistics. Query engines use this metadata to skip irrelevant files before reading data, reducing unnecessary I/O.

Iceberg uses snapshot-based versioning: each write produces a new snapshot and atomically updates the metadata pointer, so readers always see a consistent view even during concurrent writes. For TriBench, Iceberg ensures that TPC-H and custom datasets are loaded in a consistent, versioned state, so benchmark results reflect query engine behaviour rather than data inconsistencies.

\subsection{Apache Trino}

Apache Trino (formerly PrestoSQL) is a distributed SQL query engine \citep{sethi2019presto}. It uses a coordinator--worker model: one coordinator node receives queries, plans execution, and distributes work; multiple worker nodes execute the plan in parallel and read data directly from storage. Scaling the cluster means adding more workers---the query and experiment definitions stay unchanged.

CPU, memory, disk I/O, and network all affect Trino's performance. CPU is consumed by sorting, hashing, and aggregation on worker nodes. Large joins and aggregations can exhaust available memory, causing the engine to spill data to disk and increasing query time. Network throughput matters when workers exchange intermediate results between execution stages. These interactions make concurrent hardware monitoring essential: a slowdown may originate in any of these resources, and hardware metrics often surface the cause before query timings alone can explain it. Trino exposes per-query statistics---wall-clock time, CPU time, and bytes scanned---via a REST API endpoint after each query completes. TriBench collects these statistics and stores them alongside the concurrent hardware metrics.

\subsection{Kubernetes for Stateful Data Systems}

Kubernetes is the container orchestration platform enabling TriBench distributed benchmarks. The Docker backend runs all services on a single machine; the Kubernetes backend distributes Trino across cluster nodes: the coordinator pod handles query planning and orchestration, while worker pods execute data processing tasks. This allows TriBench to provision 1-worker, 4-worker, or 8-worker Trino clusters by changing a single configuration parameter, enabling performance scaling measurement without modifying experiment definitions.

Kubernetes manages the full lakehouse stack as a coordinated unit (Trino coordinator, Trino workers, Hive Metastore, PostgreSQL catalogue, MinIO object storage), providing stable network identities, persistent storage, and service discovery so components locate and connect regardless of scheduling node. This abstraction allows identical experiment specifications to run unmodified on local kind clusters or multi-node production environments (GKE). Engineers switch between Kubernetes clusters by changing kubectl context and selecting the corresponding TriBench configuration profile, enabling seamless experiment portability across development, testing, and production without modifying experiment YAML files. Chapters~\ref{chap:design} and~\ref{chap:impl} discuss TriBench's Kubernetes deployment strategy.

TriBench adopts the bundle as its primary organisational unit, adapting it for a Python-based, container-orchestrated framework. The TriBench bundle structure and how it differs from PEEL's is described in Section~\ref{sec:bundle_design}.

\section{User Scenarios}

Three scenarios model progressively more complex TriBench use cases, corresponding to the three evaluation levels in Chapter~\ref{chap:eval}. Each scenario is realised end-to-end in the evaluation, closing the loop between requirements and evidence.

\paragraph{Scenario 1 --- Local baseline (Jordan, research scientist).}
Jordan runs a local baseline to verify TriBench on a single machine before deploying to a cluster. Jordan creates a bundle, activates the Docker profile, and writes one experiment targeting five TPC-H queries at SF 1 (\textasciitilde1\,GB). Running \texttt{tribench exp run} starts the Docker stack---Trino, Hive Metastore, MinIO, and PostgreSQL---performs one warmup and three measured runs per query with host CPU, memory, disk, and network monitoring, then tears down. The run completes in under 30 minutes. Jordan exports results to CSV and confirms per-query latency and bytes-scanned are recorded alongside the hardware time series.

\paragraph{Scenario 2 --- University cluster study (Alex, researcher).}
Alex is a researcher at the University of Glasgow who wants to benchmark Trino on the university's bare-metal Kubernetes cluster (GPG). Using a bundle with a two-worker profile, Alex runs two experiments: ten TPC-DS queries at SF 1 (\textasciitilde1\,GB) and three analytical queries against a custom Parquet dataset registered in the bundle. Each experiment runs with one warmup and five measured repetitions. TriBench collects per-pod CPU and memory alongside host telemetry. The full run takes approximately one hour.

\paragraph{Scenario 3 --- Cloud scaling study and bundle sharing (Sam, DevOps engineer).}
Sam measures how Trino scales with worker count on a GKE cluster. Sam creates a bundle with a two-worker profile containing three experiments: all 22 TPC-H queries at SF 100 (\textasciitilde100\,GB), twenty TPC-DS queries at SF 10 (\textasciitilde10\,GB), and an e-commerce custom dataset. A single \texttt{tribench suite run} handles stack start-up and teardown between experiments. After the run---taking approximately three hours---Sam archives the bundle and shares it with a colleague. The colleague switches to the four-worker profile and re-runs the suite on the same GKE cluster, producing results for direct comparison against the two-worker run.

\section{Requirements Set}

Requirements are prioritised using the MoSCoW method \citep{clegg2004case}:

\begin{itemize}
    \item \textbf{M:} must-have---required for viability
    \item \textbf{S:} should-have---important but not critical
    \item \textbf{C:} could-have---desirable but lower priority
    \item \textbf{W:} won't have this time---outside project scope
\end{itemize}

\subsection{Functional Requirements}

Requirements are categorised by the five goals from Chapter~\ref{chap:intro}:

\subsubsection{Workload Execution (Goal 1)}

\begin{enumerate}
    \item \textbf{M1 --- Declarative execution:} Experiments and suites are orchestratable via YAML files without modifying framework code.
    \item \textbf{M2 --- Benchmark workloads:} The framework supplies the TPC-H and TPC-DS suites while fully supporting custom queries and user-provided datasets.
    \item \textbf{M3 --- Execution control:} Users can configure warmup runs, measured runs, per-query timeouts, and validation thresholds.
    \item \textbf{S1 --- Suite abstraction:} Multiple experiments can be grouped into suites executable as single CLI operations.
\end{enumerate}

\subsubsection{Hardware Monitoring (Goal 2)}

\begin{enumerate}
    \item \textbf{M4 --- Telemetry collection:} Host-level resources are sampled concurrently while per-query execution statistics are retrieved directly from the engine.
    \item \textbf{S2 --- Cloud metrics:} Kubernetes pod metrics are collected and normalised alongside standard hardware telemetry.
\end{enumerate}

\subsubsection{Result Storage (Goal 3)}

\begin{enumerate}
    \item \textbf{M5 --- Structured storage:} Execution results and telemetry are stored non-destructively within a relational database schema.
    \item \textbf{M6 --- Data export:} Stored benchmark runs can be exported to standard formats such as CSV, JSON, and Parquet for external analysis.
    \item \textbf{M7 --- Built-in analysis:} The framework supports basic statistical evaluation of experiments including performance, query comparison, and monitoring summaries.
\end{enumerate}

\subsubsection{Deployment Backends (Goal 4)}

\begin{enumerate}
    \item \textbf{M8 --- Lifecycle abstraction:} The framework automates the setup, execution, and teardown lifecycles across interchangeable Docker and Kubernetes backends.
    \item \textbf{M9 --- Configuration profiles:} Users can switch between deployment environments and scaling parameters without modifying the underlying experiment definitions.
    \item \textbf{W1 --- Flexible stack:} Supporting configurable lakehouse components or alternative SQL engines is out of scope due to exponential compatibility testing overhead and existing framework coverage.
\end{enumerate}

\subsubsection{Bundle Abstraction (Goal 5)}

\begin{enumerate}
    \item \textbf{M10 --- Self-contained bundles:} Benchmarks are packaged and managed as shareable directory bundles containing all necessary configurations and datasets.
    \item \textbf{M11 --- Bundle management:} The CLI scaffolds new bundles and activates them to direct all subsequent framework operations.
\end{enumerate}

\subsection{Non-Functional Requirements}

Non-functional requirements specify system qualities rather than features \citep{rahy2022understanding}.

\begin{enumerate}
    \item \textbf{M12 --- Reproducibility:} Identical experiments on identical hardware produce consistent query times and metric trends.
    \item \textbf{M13 --- Portability:} The framework executes unmodified across macOS, Linux, and Windows environments without platform-specific core logic.
    \item \textbf{M14 --- Observability:} Structured and timestamped logs are emitted at configurable verbosity levels to aid debugging.
    \item \textbf{S3 --- Low overhead:} The background monitoring subsystems perturb query execution times by less than a configurable threshold.
    \item \textbf{C1 --- Extensibility:} The modular architecture allows new deployment backends to be integrated via an abstract system interface.
\end{enumerate}

\chapter{Design}
\label{chap:design}

TriBench is organised as a five-layer architecture with two cross-cutting concerns. Each layer satisfies a distinct subset of requirements from Chapter~\ref{chap:req}; the design decisions---configuration model, backend abstraction, and concurrent monitoring---are motivated below alongside each component.

\section{Architectural Overview}
\label{sec:arch_overview}

TriBench's five layers are shown in Figure~\ref{fig:layers}: CLI, configuration, orchestration, systems, and data lakehouse. Control flows downward---a CLI command triggers configuration resolution, which parameterises orchestration, which drives system lifecycle management, which starts and stops the lakehouse services. Telemetry flows upward via two cross-cutting concerns---monitoring and result storage---that span layers three through five.

The layering addresses three non-functional requirements. \textbf{M13} (platform portability) is met by confining all platform-specific logic to the systems layer, so nothing above it contains environment assumptions. Modularity follows from each layer having one responsibility: the CLI handles input, configuration handles parameter resolution, orchestration manages execution flow, and systems manage deployment. \textbf{C1} (extensibility) is a consequence---new deployment backends require only a concrete implementation of the System abstract base class in the systems layer, with no changes elsewhere. This mirrors the separation-of-concerns rationale that \citet{diperf} applied to their controller--tester--analyser split.

\subsection{The Five Layers}
\label{sec:five_layers}

The \textbf{CLI layer} is the single entry point for all user interaction. Built on Click 8, it exposes seven command groups: bundle, sys, data, exp, result, config, and suite. A shared context object carrying the active bundle path, verbosity flag, and dry-run mode is passed through every command, ensuring all operations act on the same bundle state.

The \textbf{configuration layer} resolves parameters through a four-level HOCON hierarchy before experiment logic executes. Adapted from PEEL's layered configuration model (Section~\ref{sec:peel}), it allows engineers to switch the entire deployment context---worker count, JVM heap, storage backend---by selecting a named profile, without modifying experiment files. This satisfies \textbf{M9} (named configuration profiles) and is the mechanism behind \textbf{M13} (portability). The configuration layer is detailed in Section~\ref{sec:config_layer}.

The \textbf{orchestration layer} coordinates experiment lifecycle. It loads the resolved configuration into an experiment configuration dataclass and drives the execution loop: invoking system lifecycle methods, starting the monitoring session, submitting queries, discarding warmup results, persisting measured results, and stopping monitoring on completion. Suites---groups of experiments sharing a system lifecycle---are managed here (\textbf{M3}, \textbf{S1}). The orchestration layer is described in Section~\ref{sec:orchestration_layer}.

The \textbf{systems layer} abstracts the deployment environment behind a System abstract base class with four lifecycle methods: setup, start, stop, and teardown. Two concrete implementations are provided: a Docker backend that renders Jinja2 templates into a Docker Compose manifest and manages four services (Trino, Hive Metastore, MinIO, PostgreSQL), and a Kubernetes backend that renders manifests, applies them via kubectl, polls pod readiness, and establishes port-forwarding to the Trino coordinator. The two interchangeable backends, differing only in active profile, satisfy \textbf{M8} and \textbf{M9}. The systems layer is described in Section~\ref{sec:systems_layer}.

The \textbf{data lakehouse layer} comprises the services under test: Apache Trino, Apache Iceberg, MinIO, Hive Metastore, and PostgreSQL. TriBench provisions, configures, and tears them down as an integrated stack but does not implement them. Their architectural characteristics are described in Chapter~\ref{chap:related}; their implications for metric collection are discussed in Sections~\ref{sec:apache_trino} and~\ref{sec:kubernetes}.

\subsection{Supporting Subsystems}
\label{sec:cross_cutting}

Two subsystems serve multiple layers and are described in full later in the chapter. The \textbf{monitoring subsystem} collects hardware telemetry and per-query engine statistics concurrently with experiment execution, without blocking the query thread (\textbf{M4}, \textbf{S2}); it is described in Section~\ref{sec:monitoring_system}. The \textbf{result storage subsystem} persists query results and metric samples to a structured database inside the bundle after each run, ensuring that repeated executions accumulate without overwriting previous data (\textbf{M5}, \textbf{M6}); it is described in Section~\ref{sec:result_storage}.

\section{Open Lakehouse Stack}
\label{sec:tech_stack}

TriBench is implemented entirely in Python, taking advantage of mature libraries for system interaction (\texttt{psutil}), configuration parsing (pyhocon), database storage (SQLAlchemy), templating (Jinja2), and data export (pandas, PyArrow). A single-language architecture eliminates the need for inter-process middleware between the framework and its components, reducing both complexity and runtime overhead. 

The framework evaluates a complete open lakehouse stack. \textbf{Trino} serves as the primary distributed SQL engine, chosen because unlike Spark and Flink, it previously lacked a dedicated benchmarking harness like PEEL. The stack is completed by \textbf{Apache Iceberg} for table storage, \textbf{MinIO} for S3-compatible object storage, and a \textbf{Hive Metastore} backed by \textbf{PostgreSQL} for catalogue management. Depending on the scale of the experiment, this entire stack can be deployed locally via \textbf{Docker Compose} or distributed across a cluster using \textbf{Kubernetes}. The specific roles and implementations of these technologies are detailed within their respective layer descriptions throughout the rest of this chapter.

The CLI reads the active bundle and passes the profile selection into the configuration layer, which merges framework defaults, the chosen profile, bundle-level settings, experiment file overrides, and any CLI flags into a single resolved configuration. The orchestration layer reads this configuration, identifies the backend as Kubernetes, and starts the system: container manifests are generated and submitted to the cluster, all five pods are polled until ready, and a network tunnel to the Trino coordinator is opened on a local port. \section{CLI Layer}
\label{sec:cli_layer}

The CLI layer is the single entry point for all user interaction with TriBench. It is built on Click \citep{click}, a Python library for constructing command-line interfaces from decorated functions. Click was chosen because it handles argument parsing, help text generation, and nested command groups with minimal boilerplate, and its built-in context mechanism provides a clean way to pass shared state through a command hierarchy without global variables. The layer exposes seven command groups, each responsible for one area of the framework (Table~\ref{tab:cli_groups}). No framework code is imported or called outside these groups; all operations flow through CLI commands, ensuring consistent bundle resolution, logging, and error reporting regardless of which command is invoked.

\centering
\begin{tabular}{lp{7.5cm}l}

\textbf{Group} & \textbf{Responsibility} & \textbf{Requirements} \\
\hline

\texttt{sys}    & Start, stop, and tear down the lakehouse stack & \textbf{M8} \\
\texttt{data}   & Load datasets and manage the dataset registry & \textbf{M2} \\
\texttt{exp}    & Run experiments and select deployment profiles & \textbf{M1}, \textbf{M3}, \textbf{M9} \\
\texttt{result} & Export, display, and delete stored results & \textbf{M6}, \textbf{M7} \\

\label{tab:cli_groups}
\end{table}

For a complete reference of all sub-commands and their arguments, see Appendix~\ref{ch:appendix_cli}.

Each command has access to a shared context object, \texttt{TriBenchContext}, passed through Click's context mechanism. The context carries three fields set once at startup: the active bundle path, a verbosity flag, and a dry-run flag. All subcommands read from this context rather than managing their own state. When a bundle is active, the context also directs the results database to the bundle's results directory, so every command writes to the correct location without additional configuration.

Bundle resolution follows a fixed priority order: the \texttt{--bundle} flag takes precedence, then a state file recording the last activated bundle, then auto-detection by walking up the directory tree looking for a \texttt{bundle.yaml} file. This means commands work from inside a bundle directory without requiring an explicit path.

The dry-run flag is propagated to multi-step commands such as \texttt{sys start}, which renders templates, submits manifests to the cluster, polls pod readiness, and establishes a port-forwarding tunnel. With dry-run enabled, each planned action is printed without execution---useful for verifying configuration before committing to a long setup sequence.

\section{Bundle Abstraction}
\label{sec:bundle_design}

The bundle abstraction was designed to shield users from the complexity of the framework's directory structure. TriBench separates configuration, experiments, datasets, queries, logs, and results across multiple subdirectories---necessary for clarity within the codebase, but disorienting to a user who wants to run a benchmark without first understanding how those directories relate. A bundle presents a single named root: activate it once and every command resolves paths within it automatically. Table~\ref{tab:bundle_layout} lists the top-level elements of a TriBench bundle.

\begin{table}[H]
\centering
\begin{tabular}{llp{6.5cm}}
\hline
\textbf{Path} & \textbf{Overridable} & \textbf{Description} \\
\hline
\texttt{bundle.yaml}   & No  & Manifest: bundle name, framework version, path overrides \\
\texttt{config/}       & Yes & HOCON configuration files and named deployment profiles \\
\texttt{experiments/}  & Yes & Experiment definition files (one per experiment) \\
\texttt{apps/}         & Yes & Query files and workload assets \\
\texttt{datasets/}     & Yes & Static datasets and the dataset registry \\
\texttt{log/}          & No  & Execution logs produced by the framework and services \\
\texttt{results/}      & No  & SQLite database accumulating all run results \\
\hline
\end{tabular}
\caption{Top-level layout of a TriBench bundle. Overridable paths can be remapped in \texttt{bundle.yaml}.}
\label{tab:bundle_layout}
\end{table}

\textbf{Manifest.} At the bundle root, \texttt{bundle.yaml} records the bundle name, the framework version used to create it, and optional path overrides for any directory. At startup, the framework parses this file into an in-memory object whose properties return fully resolved absolute paths. Every layer---CLI, configuration, orchestration, storage---calls these properties rather than constructing paths directly, so a bundle can be relocated or renamed without touching framework code (\textbf{M10}, \textbf{M11}).

\textbf{Configuration.} The \texttt{config/} directory holds HOCON files defining environment parameters---worker count, memory limits, Docker or Kubernetes backend---via named profiles. Selecting a profile switches the full deployment context without modifying any experiment file. This is the TriBench equivalent of PEEL's layered \texttt{config/hosts/\$HOSTNAME/} hierarchy, adapted for named deployment profiles rather than host-specific overrides.

\textbf{Experiments and queries.} The \texttt{experiments/} directory contains one YAML file per experiment, specifying workload, dataset, warmup policy, and repetition count---the complete declarative record of what was run. The \texttt{apps/} directory holds the SQL query files referenced by experiment definitions, organised by benchmark suite (e.g., \texttt{apps/tpch/queries/}).

\textbf{Datasets.} The \texttt{datasets/} directory holds static input datasets alongside a \texttt{registry.yaml} file that maps logical dataset names to their file locations. The registry decouples experiment files from physical paths: moving or replacing a dataset requires only updating the registry, not editing every experiment that references it.

\textbf{Logs and results.} The \texttt{log/} directory receives timestamped output from the framework and the services it manages. The \texttt{results/} directory holds a single SQLite database that accumulates all run records; each run is assigned a unique identifier---experiment name, timestamp, and a short random suffix---so repeated executions append without overwriting (\textbf{M5}).

\textbf{Comparison with PEEL.} In PEEL, the framework itself---its CLI, libraries, and system binaries---is packaged inside the bundle, so no prior installation is needed. TriBench takes the opposite approach: the framework is installed once and bundles contain only configuration, queries, datasets, and results. This keeps bundles small and means one installation serves all studies. The trade-off is a version dependency; TriBench records the framework version in the manifest so recipients can reproduce results against the same release.

\textbf{Lifecycle commands.} Running \texttt{tribench bundle create} scaffolds the full directory layout and writes annotated template files into each subdirectory. This lowers the barrier to starting a new study: a user does not need to know which directories must exist before the framework will function. Once a study is complete, \texttt{tribench bundle archive} packages the entire bundle into a compressed archive (\textbf{M11}). A recipient who installs TriBench, unpacks the archive, and activates the bundle can reproduce the experiment without further setup (Section~\ref{sec:reproducibility}).

\section{Configuration Layer}
\label{sec:config_layer}

Each experiment in TriBench must be associated with a concrete set of configuration values covering both the deployment environment (Trino JVM heap, worker count, cluster address, backend type) and the workload (query timeout, run count, connection settings). Several problems arise with a na\"{i}ve approach of configuring these manually per experiment:

\textbf{Environment coupling.} Machine-specific values---heap size, worker addresses, Kubernetes context---end up embedded in experiment files. Moving an experiment to a different machine requires editing those files, breaking portability and making stored experiment artefacts machine-specific rather than workload-specific.

\textbf{Value duplication.} When running a series of related experiments on the same cluster, all but a small number of parameters remain fixed. Without a reuse mechanism, these values are copied into every experiment file and must be kept consistent manually.

\textbf{Portability breakdown.} An experiment file tuned for one environment silently breaks on another. If a colleague clones the bundle and runs the experiment on a different cluster, shared host-specific values produce wrong results or connection failures with no indication of which value is wrong.

TriBench addresses these by adopting the same layered configuration model as PEEL (Section~\ref{sec:peel}), expressed in HOCON (Human-Optimised Config Object Notation) loaded by the pyhocon library. HOCON supports comments, variable substitution, and object merging, so a profile can override a handful of parameters without restating the full configuration tree. Parameters are resolved through four ordered layers, each able to override the one below it (Table~\ref{tab:config_hierarchy}).

\begin{table}[H]
\centering
\caption{Four-level configuration hierarchy (lowest to highest precedence).}
\label{tab:config_hierarchy}
\begin{tabular}{@{}clp{7.5cm}@{}}
\toprule
\textbf{Layer} & \textbf{Source} & \textbf{Description} \\
\midrule
1 & \texttt{reference.conf}        & Framework defaults. Every valid parameter is declared here with a safe value, acting as a complete schema. \\
2 & Named profile                  & A file in \texttt{config/hosts/} describing one deployment environment: backend, worker list, JVM heap, cluster address. \\
3 & Experiment YAML                & Workload-specific parameters: query timeout, run count, session properties. \\
4 & CLI / environment variables    & Per-invocation overrides, e.g.\ \texttt{TRINO\_HOST}, for secrets or ad-hoc use. \\
\bottomrule
\end{tabular}
\end{table}

\textbf{Layer 1 (\texttt{reference.conf})} is maintained by the framework and should not be edited. It declares every valid parameter once, so any key omitted at higher layers retains a safe default.

\textbf{Layer 2 (named profile)} is the recommended primary configuration point. An engineer creates one profile per deployment environment---a laptop Docker setup, a kind cluster, a bare-metal Kubernetes cluster---and stores it in \texttt{config/hosts/}. Each profile captures the machine-specific constants that should never appear in an experiment file: backend type, worker list, JVM heap, cluster address, and Kubernetes context. Profiles can live inside a bundle's own \texttt{config/hosts/} for bundle-local environments, or in the framework-level \texttt{config/hosts/} to be shared across bundles on the same machine.

\textbf{Layer 3 (experiment YAML)} is appropriate for parameters that vary between workloads within the same environment: run count, query timeout, or a Trino session property for one experiment. It must not contain machine-specific values; if it does, the experiment ceases to be portable across environments.

\textbf{Layer 4 (CLI / environment variables)} is intentionally narrow in scope. It suits one-off overrides and secret injection in CI/CD pipelines where credentials must not be stored in files. For normal benchmark use it should be avoided: a flag is not recorded in any file, making the run harder to reproduce from stored artefacts alone.

Named profiles at layer 2 are therefore the primary mechanism for deployment context switching and portability (\textbf{M9}, \textbf{M13}). A profile states only the keys it needs to override; all other parameters fall through to \texttt{reference.conf}. Switching profiles switches the entire deployment context---worker count, JVM heap, backend, cluster address---without touching any experiment file. The same experiment YAML runs unchanged on a single-node Docker stack or a fourteen-worker Kubernetes cluster. Table~\ref{tab:profiles} lists the three profiles shipped with TriBench.

\section{Orchestration Layer}
\label{sec:orchestration_layer}

In the previous sections we explained how TriBench resolves its configuration hierarchy and how experiments are declared as YAML files within a bundle. This section describes how the orchestration layer uses those inputs to drive a complete experiment lifecycle: loading the specification, starting the deployment backend, executing queries, and handing results to storage.

\textbf{Configuration loading.} Before any experiment can run, its YAML file is loaded and merged into a single resolved configuration object. The merge follows the same three-tier precedence as the HOCON hierarchy in Section~\ref{sec:config_layer}: framework defaults, then the active named profile, then the experiment file. The result is a flat configuration that the orchestration layer reads without needing to know which layer contributed each value (\textbf{M1}, \textbf{M9}).

\begin{lstlisting}[style=yamlstyle, caption={Experiment YAML for running all 22 TPC-H queries against an Iceberg dataset.}]
name: "tpch-all-queries"
system: "trino"
connection:
  catalog: "iceberg"
  schema:  "tpch_sf1"
runs: 3
warmup_runs: 1
timeout_seconds: 120
query_files:
  - "apps/tpch/queries/q01.sql"
  - "apps/tpch/queries/q02.sql"
  # ... q03 through q22
validation:
  min_success_rate: 0.95
\end{lstlisting}

\textbf{Execution modes.} The orchestration layer exposes two execution modes. The first is a single experiment, run with \texttt{tribench exp run}. The second is a suite, run with \texttt{tribench suite run}, which groups multiple experiments under a shared system lifecycle. In the suite case, the backend stack is started once before the first experiment and torn down once after the last, avoiding repeated cold-start latency. For a single experiment, the lifecycle proceeds as follows:

\begin{itemize}
\item \textbf{Start system.} The backend is identified from the resolved configuration---Docker or Kubernetes---and its start method is called. Services are brought up, readiness is polled, and a connection to the Trino coordinator is established. The query execution step always connects to the same local port regardless of backend, which is the mechanism behind deployment portability (\textbf{M13}).

\item \textbf{Start monitoring.} A monitoring session is opened with the configured collectors. Hardware telemetry is captured in the background at the configured sampling interval, concurrent with query execution.

\item \textbf{Execute queries.} Each query in the workload is submitted for \texttt{warmup\_runs} executions first, whose results are discarded, then \texttt{runs} measured executions whose results are persisted. Warmup results never reach the storage layer, ensuring cache-warming does not bias reported latencies (\textbf{M3}). After each measured execution, query-level statistics are read from Trino's response: wall-clock time, CPU time, bytes scanned, peak memory, and spilled bytes. Both wall time and CPU time are stored---wall time captures end-to-end latency, while CPU time isolates compute work on the workers, independent of scheduling or network delays (\textbf{M4}).

\item \textbf{Stop monitoring and persist results.} The stop signal is sent to all collector threads. Once they have drained their buffers and exited, the full set of metric samples is written to the result database alongside the run record, which includes query success rate, total execution time, and a snapshot of the resolved configuration (\textbf{M5}). The run identifier format is described in Section~\ref{sec:result_storage}.

\item \textbf{Stop system.} The system stop method is called in a \texttt{finally} block, ensuring teardown occurs even if an exception is raised during query execution.
\end{itemize}

\textbf{Portability.} The orchestration layer calls only the four lifecycle methods on the System base class and reads only the resolved configuration object. It contains no Docker- or Kubernetes-specific code, so switching backends requires only a profile change with no modification to the orchestration logic. This is the structural consequence of the layering described in Section~\ref{sec:arch_overview}.

\section{Monitoring System}
\label{sec:monitoring_system}

The monitoring system captures hardware telemetry concurrently with query execution without blocking the query thread. Each metric source implements a MetricCollector interface with start, stop, and collect methods; a central MonitoringSession starts all collectors and runs a single background thread that calls collect on each at the configured sampling interval, appending samples to a shared list. Three collectors are provided: a host resource collector that samples CPU, memory, disk I/O, and network I/O using psutil (\textbf{M4}); a Kubernetes pod collector that queries per-pod CPU and memory from the cluster and gracefully disables itself if the cluster metrics service is unavailable (\textbf{S2}); and a query statistics collector that reads Trino's per-query response after each execution---CPU time, bytes scanned, peak memory, and spilled bytes (\textbf{M4}). On shutdown, a stop flag breaks the sampling loop, the thread is joined to ensure no samples are lost, and all buffered metrics are flushed to the result database before the run record is finalised. \section{Systems Layer}
\label{sec:systems_layer}


\textbf{Backends.} The systems layer is responsible for managing the lifecycle of the infrastructure that experiments run on. TriBench supports two deployment backends. The Docker backend targets local single-machine deployment, making it straightforward to run benchmarks on a development machine without any cluster setup. The Kubernetes backend is designed for truly distributed deployments, where Trino distributes query execution across multiple worker nodes to better reflect production-scale lakehouse environments.

\textbf{Cluster targeting.} The Kubernetes system can target any available cluster---a local cluster for development or a remote managed cluster such as Google Kubernetes Engine---by pointing it at the appropriate Kubernetes context in the active profile. Switching clusters requires no changes to the experiment or the framework.

\textbf{Lifecycle abstraction.} Both backends expose the same lifecycle operations to the orchestration layer: set up, start, stop, and tear down. The System abstract base class defines exactly these four methods, plus a status query. The orchestration layer calls only these and contains no Docker or Kubernetes API code of its own. Adding a third backend requires only a new subclass with no changes elsewhere (\textbf{C1}). Figure~\ref{fig:system_lifecycle} shows the lifecycle state machine that both backends implement.

\textbf{Shared stack.} Both backends deploy the same four services: Trino, Hive Metastore, MinIO, and PostgreSQL. Hive Metastore, backed by PostgreSQL, provides the Iceberg catalogue layer; PostgreSQL stores the catalogue state so it survives restarts within an experiment session. MinIO is an S3-compatible object store. Trino's Iceberg connector communicates using S3 semantics, so MinIO provides identical connectivity to Amazon S3 without requiring cloud credentials or network access. This is what enables local reproducibility (\textbf{M12}): the full stack runs on a single machine with no external dependencies.

\textbf{Docker.} Setup generates all required configuration files and a service definition file from the active profile values, so the running configuration always reflects the current experiment settings without manual editing. Start brings all four services up and performs a two-stage readiness check: it waits for the containers to be running, then waits for the Trino coordinator to confirm it is ready to accept queries. This prevents experiments from starting prematurely. Stop shuts services down gracefully; teardown optionally removes stored data, allowing a clean slate for the next experiment session (\textbf{M8}).

\textbf{Kubernetes.} Setup generates deployment manifests for each service from the active profile, including Trino's configuration. The number of Trino worker replicas is taken from the profile, or detected automatically from the available nodes in the target cluster. Start deploys services in dependency order---object storage first, then the catalogue, then Trino---waiting for each to be healthy before bringing up the next. Once the cluster is running, a port-forwarding tunnel is established automatically so the client can reach the Trino coordinator at a fixed local address regardless of how the cluster is configured or where it is hosted. If the tunnel is interrupted---by a network drop or terminal restart---it can be resumed independently with \texttt{tribench sys port-forward} without touching the cluster. The client connects to the same local address in both backends, which is the mechanism behind deployment portability (\textbf{M13}): the query execution code is identical regardless of deployment target.

\section{Result Storage}
\label{sec:result_storage}

The results of every experiment run are stored in a relational database that persists across sessions. Each run produces three categories of records: per-query execution results containing timing and Trino engine statistics, a time-series of hardware telemetry samples captured during execution, and a run-level summary with overall status and resource totals. Runs are linked to a named experiment record, so executing the same workload twice appends a new run rather than overwriting the previous one. The schema is detailed in Table~\ref{tab:result_schema}. The stored data can then be explored using the built-in analysis commands or exported for use with external tools.

\textbf{Database Backends.} TriBench supports two database engines depending on the scale and environment of the experiment. For local development and single-user experiments, \textbf{SQLite} is the default: no configuration is required, and the database file is automatically created inside the active bundle. For multi-user environments, shared infrastructure, or massive workloads that accumulate large volumes of telemetry data, a standalone \textbf{PostgreSQL} instance can be configured. Because the storage layer relies on an ORM, switching between the two requires only changing a configuration variable with no modifications to the framework code or the database schema.

\textbf{Analysis and Export.} TriBench ships with a suite of built-in analysis commands that run directly against the stored results without requiring a manual export step (\textbf{M7}). The \texttt{tribench res analyze} suite allows users to compute descriptive statistics and flag outliers (\texttt{statistics}), evaluate overall throughput and execution time (\texttt{performance}), and perform statistically significant head-to-head t-test comparisons between experiments (\texttt{compare}). It can also detect query slowdowns for CI pipeline integration (\texttt{regression}) and calculate parallel efficiency when scaling worker counts (\texttt{scalability}). For analysis outside the framework, \texttt{tribench res export} converts the relational data into flat CSVs for spreadsheets, rich JSON documents containing configuration metadata, or columnar Parquet files suited for large-scale processing tools like pandas or Apache Spark.

\section{Experimental Setup}
\label{sec:eval_setup}

\subsection{Local Environment (Level 1)}

Level 1 experiments run on an Apple MacBook with an M4 chip, 24\,GB unified memory, and an NVMe SSD, running macOS Sequoia. Docker Desktop provides the container runtime. The Trino image is version 434; the coordinator is allocated a 4\,GB JVM heap via \texttt{docker.conf}. All Level 1 artefacts---experiment definitions, configuration, datasets, and results---are contained in a bundle named \texttt{tpch-docker}, created with \texttt{tribench bundle create tpch-docker}. The TPC-H SF 1 dataset is used, stored as Parquet files in MinIO and catalogued through Hive Metastore backed by PostgreSQL. The entire stack is started automatically by \texttt{tribench sys start}.

\subsection{Bare-Metal Kubernetes Environment (Level 2)}
\label{sec:eval_gpg}

Level 2 experiments run on the University of Glasgow GPG bare-metal Kubernetes cluster. All Level 2 artefacts are contained in a shared bundle named \texttt{tpcds-gpg}, created with \texttt{tribench bundle create tpcds-gpg} and shared between Alex and Taylor via the same working directory. Storage is provided by a Ceph block device via the Rook operator; the Kubernetes Metrics Server is deployed to enable per-pod CPU and memory collection. TriBench connects to the cluster via \texttt{kubectl port-forward} to \texttt{localhost:8080}, established automatically by the Kubernetes backend. A single profile is used: \texttt{gpg-multinode.conf} configured for two workers with a 16\,GB coordinator heap. The TPC-DS SF 10 dataset is loaded alongside a custom domain dataset registered in the bundle's dataset registry.

\subsection{GCP GKE Environment (Level 3)}
\label{sec:eval_gke}

Level 3 experiments run on a Google Kubernetes Engine cluster. All Level 3 artefacts are contained in a bundle named \texttt{gke-suite}, created with \texttt{tribench bundle create gke-suite}. GKE is used for the worker scaling study because node provisioning is elastic and each worker count can be reproduced cleanly by changing the workers list in \texttt{gcp-gke.conf} without manual cluster reconfiguration. The scaling study sweeps one, two, and four workers on a fixed set of TPC-H queries; the subsequent suite run uses four workers throughout. GKE's built-in Metrics Server provides per-pod telemetry. Four datasets are loaded: TPC-H SF 100, TPC-DS SF 100, and two custom domain datasets. After the run, the bundle is archived for reproduction: \texttt{tribench bundle archive gke-suite}.

\subsection{Note on KinD (Local Kubernetes)}

TriBench also supports Kubernetes-in-Docker (KinD) via the \texttt{kind.conf} profile, which provisions a multi-node Kubernetes cluster entirely within Docker containers on a local machine. Because all KinD nodes share the host's physical CPU and memory, the resulting query latency figures do not represent distributed execution and are not used as primary evaluation data. KinD is nonetheless useful for confirming that the Kubernetes backend, per-pod metric collection, and port-forward connectivity work correctly without requiring cluster access, providing additional evidence for deployment portability (\textbf{M13}). Users without an institutional or cloud cluster can substitute \texttt{kind.conf} for \texttt{gpg-multinode.conf} or \texttt{gcp-gke.conf} and run any Kubernetes experiment unchanged.

\section{Framework Overhead}
\label{sec:eval_overhead}

TriBench's monitoring subsystem runs in a background thread, polling host metrics via \texttt{psutil} and, on Kubernetes, querying the Metrics Server API once per monitoring interval. To confirm that this instrumentation does not materially perturb query execution (\textbf{S3}), a dedicated overhead experiment was run across all three deployment environments.

\subsection{Method}

Two run configurations were compared per environment:

\begin{itemize}
    \item \textbf{Run~A --- instrumented:} all monitoring enabled (\texttt{monitoring.enabled~=~true}), polling at a 1-second interval with per-pod Kubernetes metrics active where applicable.
    \item \textbf{Run~B --- uninstrumented:} monitoring disabled (\texttt{monitoring.enabled~=~false}); the framework submits queries and records wall-clock times but collects no background telemetry.
\end{itemize}

Three TPC-H queries at SF~1 were used: Q1 (full lineitem scan, 6\,M rows), Q6 (filter-only, lightweight), and Q18 (aggregation with a join and subquery). These cover the range from scan-bound to CPU-bound workloads. Five measured runs were collected per configuration, preceded by one warmup run that was discarded. Overhead is defined as:
\[
    \text{overhead} = \frac{\overline{t_A} - \overline{t_B}}{\overline{t_B}} \times 100\%
\]
where $\overline{t_A}$ and $\overline{t_B}$ are the mean execution times for Run~A and Run~B respectively.

\subsection{Discussion}

Across all three environments, measured overhead is below the 5\% target (\textbf{S3}). Docker shows the highest overhead at 3.8\%, which is expected: \texttt{psutil} process-tree scanning runs at a fixed polling rate, so its cost is proportionally larger when individual queries complete in under half a second. The additional Kubernetes Metrics Server API call introduced by per-pod collection (\textbf{S2}) does not produce a statistically distinguishable cost at the query durations tested on GPG or GKE. These results confirm that TriBench's background monitoring is safe to leave enabled during production benchmark runs without materially affecting the latency figures under study.

\section{Level 1: Local Docker Baseline}
\label{sec:eval_l1}

This section demonstrates TriBench's core benchmarking workflow on a local Docker environment, corresponding to the researcher scenario described in Section~\ref{sec:scenarios}: a user with no cluster access who wants to establish a reproducible TPC-H baseline on a laptop.

\subsection{Deployment and Configuration}

TriBench requires no manual Docker Compose authoring for this scenario. The user creates a self-contained bundle and points it at the built-in Docker profile:

\begin{verbatim}
tribench bundle create tpch-docker
tribench sys start --profile docker.conf
\end{verbatim}

\noindent The \texttt{docker.conf} profile is included in the TriBench distribution and configures a Trino~434 coordinator with a 4\,GB JVM heap, Hive Metastore backed by PostgreSQL~15, and MinIO as the object store. The full stack---five containers in total---reaches a ready state in under 90 seconds. The TPC-H SF~1 dataset (~320\,MB of Parquet files) was loaded into MinIO and registered with the Iceberg catalogue in a single command:

\begin{verbatim}
tribench data load --dataset tpch-sf1-iceberg --bundle tpch-docker
\end{verbatim}

\noindent No additional configuration was required. This demonstrates that TriBench's Docker backend handles the full lifecycle---network creation, container scheduling, port binding, and health checking---without user intervention (\textbf{M11}).

\subsection{Experiment Execution}

The experiment was defined in \texttt{tpch-all.yaml}, a declarative YAML file specifying all 22 TPC-H queries, three measured runs, one warmup run, a 60-second per-query timeout, and a minimum success rate threshold of 95\%:

\begin{verbatim}
runs: 3
warmup_runs: 1
timeout_seconds: 60
validation:
  min_success_rate: 0.95
\end{verbatim}

\noindent The experiment was launched with a single command:

\begin{verbatim}
tribench exp run tpch-all --bundle tpch-docker
\end{verbatim}

\noindent All 22 queries completed successfully across all three measured runs (66 executions in total). Mean query latency ranged from 0.17\,s (Q6, filter-only) to 0.60\,s (Q13, aggregation with a correlated subquery). The three slowest queries---Q13 (0.60\,s), Q21 (0.53\,s), and Q8 (0.44\,s)---are all join-heavy or involve large intermediate result sets, consistent with expected TPC-H behaviour at SF~1. Figure~\ref{fig:tpch_docker} shows the mean execution time for all 22 queries.

\begin{figure}[h]
    \centering
    \includegraphics[width=\textwidth]{figures/fig7_1_tpch_docker}
    \caption{Mean TPC-H query execution times on Docker (SF~1, 3 measured runs). Error bars show the range across runs. All 22 queries completed within the 60-second timeout.}
    \label{fig:tpch_docker}
\end{figure}

\subsection{Host Monitoring}

With \texttt{monitoring.enabled~=~true}, TriBench's background collector polled host CPU and memory at a 2-second interval throughout the run, recording each sample against its wall-clock timestamp. Query boundaries were recorded automatically so that per-query resource windows can be reconstructed from the results database. Figure~\ref{fig:docker_timeseries} shows CPU utilisation over the duration of the experiment, with vertical lines marking the start of each query group.

\begin{figure}[h]
    \centering
    \includegraphics[width=\textwidth]{figures/fig7_2_docker_timeseries}
    \caption{Host CPU utilisation during the Level~1 TPC-H experiment (Docker, SF~1). Vertical dashed lines mark query-group boundaries. The Trino JVM is the dominant CPU consumer; idle periods between queries are visible.}
    \label{fig:docker_timeseries}
\end{figure}

\noindent CPU utilisation peaks are clearly correlated with query execution, and the idle troughs between queries confirm that the monitoring captures genuine workload signal rather than background noise. This provides direct evidence for host telemetry collection (\textbf{M6}) and per-query statistics (\textbf{M7}).

\subsection{Result Storage and Export}

Results were stored automatically in the bundle's SQLite database (\texttt{tpch-docker/results/tribench.db}) using a relational schema with four linked tables: \texttt{Experiment}, \texttt{ExperimentRun}, \texttt{QueryExecution}, and \texttt{MonitoringMetric} (\textbf{M8}). Re-running the experiment a second time without clearing results produced a new run ID rather than overwriting the previous data, confirming non-overwriting accumulation (\textbf{M10}):

\begin{verbatim}
$ tribench result list --bundle tpch-docker
  Run 1  tpch-all  2026-03-11 19:03:34  22 queries  success
  Run 2  tpch-all  2026-03-11 19:09:12  22 queries  success
\end{verbatim}

\noindent Results were exported to CSV for downstream analysis (\textbf{M9}):

\begin{verbatim}
tribench result export --bundle tpch-docker --format csv
\end{verbatim}
